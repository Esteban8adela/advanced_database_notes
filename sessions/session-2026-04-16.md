## What I understood
- Indexes aren't always faster. Oracle opts for a Full Table Scan if an index query returns too large a percentage of the table (e.g., querying low cardinality columns like `site_id` or very large date ranges).
- Composite indexes (like `patient_id`, `visit_date`) are generally only used if the query filters on the *leading column* (`patient_id`). You can't just search by the trailing column and expect the B-tree index to work efficiently.
- Applying a function to a database column in a `WHERE` clause (like `TO_CHAR(patient_id)`) breaks the standard index. Functions should be applied to the parameter/literal instead.
- Indexes speed up `SELECT` statements but slow down `INSERT`/`UPDATE`/`DELETE` operations, requiring different strategies for high-transaction OLTP tables versus nightly-loaded reporting tables.
